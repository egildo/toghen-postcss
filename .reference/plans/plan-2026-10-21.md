## 1. Findings: the postcss adapter against the new core

### What it still computes that the core answers, or should

1. **The tokens one level under a group, from a prefix filter.** `group()` at `src/index.ts:1632-1636` filters
   `getAllPaths()` by prefix and depth. That is `Collection.childrenOf()`. The lib's decision of 21 October says the
   CSS adapter's prefix filter was deleted; this copy survived. Fix: ask `childrenOf()` and keep the tokens.
2. **The groups of a collection, from token paths.** `spellings()` at `src/index.ts:1382-1386` builds every group
   by slicing token paths. The lib records it as "still re-derived, one consumer" (the review's question 7). It
   need not be: a walk down `childrenOf()` from the root is the core's answer. Fix: walk `childrenOf()`.
3. **The token that owns a member path, twice.** `ownerOf()` at `src/index.ts:777-788` and `ownerOfRef` at
   `src/index.ts:1439-1443` both walk segments with `getNodeKind()`. The core walks the same in `resolveValue()`
   (the review's question 8, absorbed into the value question) but answers it to no one. Only postcss asks, so by
   the rule it stays in the adapter. Fix: one copy, not two.
4. **A leftover wrapper.** `defaultsOf()` at `src/index.ts:862-864` now only calls `getDefaultMode()`. Delete it.
5. **Raw step values, normalized by both adapters.** `chains()` at `src/index.ts:1509` calls
   `normalizeTokenValue(type, step.value, path)` with a type it finds itself at `src/index.ts:1436` (the first
   type met across the modes). The Figma adapter does the same at `toghen-figma/main/utils/sum.ts:465,469,513`.
   Two consumers re-derive the stored shape of a chain's values. This should enter the core (see question 9).
6. **Checked and left with the adapter, one consumer each:** which component resets a re-pointed token, the
   outermost (`repointed()`, `src/index.ts:620-641`); whether a link is conditional (`src/index.ts:1518`) and
   which tokens a chain covers (`src/index.ts:1520`), both already open in postcss's decisions; whether two modes
   write the same CSS (`sameIn()`, `src/index.ts:1597`); the members a composite declares (`longhands()`,
   `memberProperties()`).

### Does the output follow the model and the precedence ruling

7. **Mixins, local properties, when-mixins, layers, context selectors: they follow `model.md`.** A mixin per group
   with its resets, rest, `@contents`, then parts (`built()`, `src/index.ts:1263-1289`); `--_name` reset to
   `initial` in the component (`resets()`, `src/index.ts:1250-1258`); `--when-<modifier>-<context>` as
   `&:where(S, S *)` (`src/index.ts:1325-1338`); a `defaults` sublayer and one per modifier
   (`contexts()`, `src/index.ts:1025-1130`); spellings from `getContextSelector()`.
8. **Precedence: the CSS agrees with the ruling only while every spelling weighs the same.** The ruling is: more
   matching parts win, then the latest differing axis in vocabulary order. The CSS gets "more parts" from nesting,
   which adds each spelling's specificity, and the tie from rule order. An at-rule spelling adds no specificity,
   and neither does `:where()`. A probe (synthetic, not committed) with the axes `variant`, `state`, and `input`
   spelled `@media (pointer: fine)`: under *primary, hover, fine*, `Collection.applies()` answers
   `button.primary.fine.background`. The expanded CSS writes `.b[data-variant='primary']` inside the media rule,
   at (0,2,0), before `.b:hover`, also (0,2,0). Hover wins in the browser. The same holds for a `:where(.calm)`
   spelling. The running example agrees, because its button's spellings all weigh one class. The parts fixture
   already carries an at-rule axis (`test/parts.test.ts:23`) but no token combines it with another part.
9. **One case the core cannot be asked.** Two values of one axis can match at once in a browser (`:hover` with
   `:active`). The CSS lets the later value win, as `model.md` says. `applies()` takes one value per axis, so it
   has no answer there. Not a defect; the docs should say the CSS decides it.
10. **What the tests prove, and in which shapes.** Part order by the vocabulary: `test/parts.test.ts:105-152`,
    structured colours, asserted on the mixin text. Cascade outcomes: `test/equivalence.test.ts:241-300`,
    structured colours, rem dimensions, a `fontFamily` array, against the frozen old output, never against
    `applies()`. Layer order: `test/layers.test.ts:64,121`, with structured shapes at `:112`. **Missing:** a test
    that compares the cascade with `applies()`; a two-part token with an at-rule or `:where()` spelling; and any
    postcss test whose `resolutionOrder` differs from the declared order. Every fixture lists its modifiers in
    `resolutionOrder` as declared (`test/chain.test.ts:31` and the others), so the reason `'precedence'` exists
    is not tested in this package.
11. **When-mixins and spellings use the precedence order.** `modifiersOf()` (`src/index.ts:870-872`) is used for
    the blocks and layers, where the cascade needs it (`:1031`), but also for the `--when-` mixins (`:1326`) and
    the spellings (`:1400`), which only list. The core's contract is the declared order; those two should follow it.
12. **A message that no longer fires.** With a collection built by hand, `modifiersOf()` returns none, so
    `chains()` is never called and its refusal at `src/index.ts:1429-1432` is dead. `bind: 'chain'` on such a
    collection now writes plain blocks without a word. The test was deleted in `78a9cb1`; the message is still
    in `reference.md:462`.

### The open question: `getModifiers('precedence')`

18. **Postcss needs one document-wide order, and the chains cannot give it cheaply.** The blocks and the
    `@layer defaults, theme, density;` statement are per stylesheet. A chain is per token: its links run
    last-winning first, so each token gives a partial order of the modifiers that define it.
    - *Ordering from the chains* costs a merge of partial orders over every token, and over the chains of the
      tokens they refer to (under `references: 'resolve'` a token is written in the block of a modifier it only
      reaches through a reference). Modifiers that no token links need a tie rule. Worse, `@toghen contexts button`
      and `@toghen contexts field` would derive different orders from different tokens, and the plugin already
      refuses a second order statement that differs in one layer (`src/index.ts:1049-1051`). It re-derives what
      `resolutionOrder` states in one line.
    - *Keeping it* costs one argument and one exception to the sentence "the modifiers have one order".
    - Recommendation: keep it, close the question, and let the prompt's `system` question print the order the
      modifiers win in. That makes two consumers, and it is what a person debugging a cascade asks.

### Where the seam is thin

19. **Errors the core throws untyped.** The vocabulary errors (`toghen-lib/src/core/collection.ts:758,874,879`)
    and the spelling errors (`toghen-lib/src/resolver/context-selector.ts:45,51`) are plain `Error`. Postcss
    recognises the library's sentence by `err.constructor === Error` (`src/index.ts:1693`), which also catches any
    other plain error. The lib's reference says every error is a named export.
20. **Errors the adapter builds or rewrites.** `collectionOf()` constructs a core `CollectionNotFoundError`
    (`src/index.ts:875-880`); `ownerOf()` a `PathNotFoundError` (`:788`); `inCollection()` swallows the core's
    error from `lookupPath()` and lets a later call fail with another message (`:853-859`); `chains()` reads a
    `PathNotFoundError` from `contextsOf()` as "a token added by hand" (`:1468-1473`).
21. **Mode names built as text for the core to parse.** `collection.modeNamed(\`${modifier.name}=${context}\`)`
    at `src/index.ts:1052,1067,1099`. The core has `getModeName(input)` on the resolver, which takes the pair.
22. **A copy of a core naming rule.** `ident()` (`src/index.ts:1765-1767`) is the escape inside `cssLinkName()`
    (`toghen-lib/src/utils/css-name.ts:52`). Postcss alone writes flags and when-mixins, so it stays, but it
    should call one shared spelling rather than copy it. Small.
23. **Raw values crossing in chain steps:** finding 5.

## 2. The loading chapter, as designed

### What the standard says, point by point

| Ruling | Where it meets the W3C resolver module | Where it needs care |
|---|---|---|
| Three forms | The token-file form becomes a one-set document: `version` `2025-11-01`, one set whose `sources` reference the files (§ Sets allows file references), `resolutionOrder` naming that set. Array order is merge order and the last wins, which the standard requires. | The wrapper must sit, in memory, in the files' folder, so relative references and `origins` read as if an author had written it there. A string entry that is a token file must be told from a resolver document: `Array.isArray(resolutionOrder)`, as `load` already does. |
| The overrides map | It lives outside the document, as a load option. The document and its bundle (`JSON.stringify`) stay standard; the bundle holds the swapped content. A `$ref` resolves against the holding document's location, as JSON Schema does; the map acts before that, on the text. Import maps do the same with specifiers. | Import maps resolve a value against the map's own location; the ruling resolves it against the holder, so one relative value names a different file in each folder. One key catches the same text in every holder. A key is the whole `$ref`, fragment included, so `a.tokens.json` does not catch `a.tokens.json#/color`. A same-document pointer (`#/sets/base`) is a key like any other. A mapped reference must pass the same checks as a written one: no scheme, not into `#/resolutionOrder/…`, no set naming a modifier. |
| The collision report | The standard says two sources of one set may declare one token and the last wins. The report changes nothing; it advises. `resolutionOrder` says later items override earlier ones, so collisions there are the intent and are never reported. | A modifier's context is also a list of sources with the same rule. A set's source may itself be a pointer to another set, whose sources then count as this set's. A token is merged per path, so only two sources that both give a `$value` collide. |
| An overlay | A set's sources and `resolutionOrder` may reference another JSON document; Toghen already copies a named set or modifier of another resolver document in. The standard forbids a reference into `#/resolutionOrder/…`, so an order can never be borrowed: the overlay states its own. (The standard does not say "never read"; it forbids the pointer. Toghen's "only the named item comes across" is its own rule built on that.) | The base's inline sets and modifiers cannot be borrowed: the standard forbids referencing them. An overlay cannot add a source to a borrowed modifier's context; it redeclares the modifier, and a modifier with the base's name and different contexts is the existing "two modifiers, one name" error. The collection takes the overlay's `name`. |
| A map value that is a resolver | Today `load` copies a set or modifier a reference names in another resolver. A mapped reference behaves the same. | A map that sends a token file's reference to a whole resolver document, with no fragment, is the existing error "names a resolver document", and the message must name the written reference, its holder and the location read. A map that sends a `resolutionOrder` item to a token file would put tokens where the standard wants a set or modifier: refused. |
| Rejected: `extends` | The resolver module has no such keyword. | Not to be confused with the format's `$extends` on groups (§6.4), still on the lib's roadmap. |

### The API

```typescript
// A resolver document, or one token file; or several token files, merged in the order given.
function load(entry: string, options: LoadOptions): Promise<LoadResult>;
function load(entries: string[], options: LoadOptions): Promise<LoadResult>;

interface LoadOptions {
  /** The text at `location`. Rejects when there is none. Unchanged. */
  read(location: string): Promise<string>;
  /** Token files only: the collection's name. Default: the name of the folder that holds the files. */
  name?: string;
  /** A `$ref` as written → the location to read instead, resolved against the document that holds the `$ref`. */
  overrides?: Record<string, string>;
}

interface LoadResult {
  /** A valid W3C resolver document, every file reference resolved. Unchanged. */
  document: ResolverDocument;
  /** Each token path to the files read that define it. Unchanged; under a map, the files read. */
  origins: Map<string, string[]>;
  /** New: every file reference followed, in the order met. */
  reads: Array<{
    ref: string;          // the $ref as written
    holder: string;       // the document it is written in
    location: string;     // the file read
    overridden: boolean;  // whether the map sent it there
  }>;
  /** New, when a map was given. */
  overrides?: {
    hash: string;         // FNV-1a, 64 bits, of the map with its keys sorted: 16 hex digits
    unused: string[];     // keys no reference matched: a typo in a map is otherwise silent
  };
  /** New: the check question's collision rows. */
  collisions: Collision[];
}

interface Collision {
  path: string;           // the token path, collection-relative
  set: string;            // the key in document.sets, or `<modifier>/<context>` (see question 3)
  files: string[];        // the files that give it a $value, in merge order; the last wins
  redundant: boolean;     // every one gives the same $value, as written
}
```

- The token-file form writes, in memory, at `<folder>/<name>.resolver.json`:
  `{ "version": "2025-11-01", "name": <name>, "sets": { "base": { "sources": [{ "$ref": "<file>" }, …] } },
  "resolutionOrder": [{ "$ref": "#/sets/base" }] }`. `document` returns it, with the files inlined. A person can
  save it and grow it into a resolver document.
- The default name is the base name of the folder that holds every file. When the files share no folder, the
  name must be given; `load` says so.
- The hash needs no dependency: FNV-1a is a dozen lines, and lib's only dependency stays `culori`. Two runs with
  one map give one hash, whatever the key order.
- Where `check` asks: `load().collisions`, because only `load` knows files. The specs' question table adds `load`
  to the answerers of the check question. See question 2 for the alternative.

### The overlay, in the running example

A synthetic theme with a warmer accent, beside the base, `toghen-lib/example/ds.warm.resolver.json`:

```json
{
  "version": "2025-11-01",
  "name": "ds",
  "description": "The running example with a warm accent: the base's layers, and one set of its own.",
  "sets": {
    "warm": { "sources": [{ "$ref": "warm.tokens.json" }] }
  },
  "resolutionOrder": [
    { "$ref": "ds.resolver.json#/sets/base" },
    { "$ref": "#/sets/warm" },
    { "$ref": "ds.resolver.json#/modifiers/theme" },
    { "$ref": "ds.resolver.json#/modifiers/density" }
  ]
}
```

`warm.tokens.json` redefines `surface.accent`. The dark theme still wins in dark, because the overlay's order puts
the theme after its own set: the order is the overlay's to state. The same theme by map, on the base:
`warm.overrides.json`, `{ "roles.tokens.json": "roles.warm.tokens.json" }`, where `roles.warm.tokens.json` is a whole
copy of the roles with the warm accent. The base document is unchanged.

`ds-striped.resolver.json` stays as it is. It adds sources inside the theme's and the density's contexts, which an
overlay cannot do to a borrowed modifier. Its decisions entry says so.

### Rejected or parked, to record in the lib's decisions

- **An `extends` keyword.** The overlay is a second standard document; nothing new is needed.
- **CSS-style layer names on sets.** Syntax over the standard; nothing asks for it.
- **A second seam for the swap.** The map is defined in terms of `read`: it changes which location `read` is asked
  for, and nothing else.
- **Scopes in the map**, as import maps have, to give one key two meanings by holder. Parked until a map needs it;
  `reads` shows which holder read which file.
- **A folder as a form** (`load('tokens/')`). Parked: it needs a listing callback beside `read` (question 1).

## 4. Risks and questions for the maintainer

Blocking, before Phase 2:

1. **The three forms.** I read them as a resolver document, one token file, and a list of token files. Or is the
   third a folder? That needs a listing callback beside `read`, a second seam.
2. **Where the collision report lives.** In `load()`'s result (recommended: only `load` knows files), with the
   specs naming `load` among the check question's answerers. The alternative carries the per-source files into
   `Resolver`, so `Collection.check()` can report them; that adds provenance to the core's model.
3. **Collisions inside a modifier's context.** The standard gives a context's sources the same last-wins rule as a
   set's. Recommended: report them too.
4. **Redundant means equal as written.** `"#ffffff"` and `{ colorSpace: "srgb", components: [1, 1, 1] }` would not
   count as redundant. Normalizing needs the inherited `$type` at load time. Recommended: as written.
5. **The map's keys and values.** Recommended: a key is the whole `$ref`, matched exactly; a relative value is
   resolved against the holder, as the ruling says, though import maps resolve against the map; `unused` keys
   reported.
6. **The precedence limit (finding 8).** (a) Write rules with more parts after rules with fewer, whatever their
   nesting: matches the ruling for at-rule and `:where()` spellings, changes the mixins' shape and some golden
   output. (b) Warn when a part token with two or more parts has an at-rule or `:where()` spelling. (c) State the
   limit in the docs and pin it in a test. Recommended: (b) and (c) now, (a) when a consumer meets it.

## 6. What the build found (22 October 2026)

All eleven units are merged on `loading-chapter`, one merge each, in waves: units 1, 2, 4; then 3, 5, 6; then 7, 8
(and a fix to unit 6); then 9, 10; then 11. After every merge: typecheck, test and build were green; the plugin's
stylesheet and `toghen-ui`'s held no `[object Object]` and no `toghen(`; the diff named no consumer. Final counts:
lib 457, postcss 353, query 21, ui 45, figma 1247.

- **Precedence (unit 6): the ruling is met for rules with as many parts, not between them.** Rules with more parts
  now come after rules with fewer, so a two-part token with an at-rule or `:where()` spelling wins as `applies()`
  says. But order decides only between rules of equal specificity. A one-part `:hover` rule still beats a one-part
  at-rule or `:where()` rule declared later in the vocabulary, where the core picks the later one. The docs and
  postcss's decisions state it. The fuller fix, every part rule at one specificity (spellings wrapped in
  `:where()`), changes how parts meet hand-written rules and needs a ruling. Open.
- **Unit 6's output broke a `toghen-ui` test.** The cause was older: `toghen-ui`'s build pasted each file at
  column 0 inside its layer, so the plugin's nested rules closed at column 0 and the test cut the button's rule
  short. Fixed in `toghen-ui/scripts/build.mjs` (each pasted file indented one step); the test is unchanged.
- **`load` refuses more than before (unit 5):** an item of `resolutionOrder` that names tokens, even when written,
  not only when mapped; an entry referring to itself with no fragment; a map value that is not a string.
- **Collisions (unit 7):** a collision inside a set that other sets point at is reported under that set and under
  each set pointing at it; array order counts for "equal as written".
- **Errors (unit 10):** `normalizeTokenValue()` now throws `InvalidTokenError` where it threw a plain error. One
  side effect not covered by a test: inside a directive, postcss now words an interpolation error
  (`InvalidInterpolationError`, a kind of `InvalidTokenError`) as "Cannot write the … of …" rather than "Cannot
  resolve token …". Left for review. `DesignSystem.addCollection()` still throws plain errors: no existing class
  fits.
- **Chain values (unit 11):** each step's type is read with the step's modifier at its context and every other at
  its default. The values are normalized when `contextsOf()` answers, not when the chain is built, since building
  them earlier made `valueAt()` refuse tokens the resolver accepts. `toghen-lib/core-review.md` still lists postcss
  as a user of `normalizeTokenValue`; left as the review's record.
- **The prompt (unit 9):** a blank line now ends an answer; file paths print relative to the entry's folder; the
  query package's open question on several documents per session is closed.
- **Not done:** version bumps (the maintainer's), and the Figma command line's `--overrides` (out of this round).
